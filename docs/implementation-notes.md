# 実装メモ(仕様の解釈と、決めたこと)

仕様書(`spec.md`)で明示されていなかった点について、どう実装したかを残します。
仕様と食い違う判断は入れていません。判断が必要だった箇所だけを挙げます。

## 要点

- 迷ったところは「重複を見逃さない側」に倒しています。営業不可(即時停止)にする条件だけは慎重にしています。
- 施設名が入っている場合は「企業全体」と「その施設だけ」を区別します。
- 保護期間はすべて日数で持ちます。残り日数は保存しません。
- 判定・計算はすべて `src/domain/` の純粋な関数です。画面・保存先を差し替えても結果は変わりません。

---

## 1. 重複判定(§4)

### 1-1. 企業名の完全一致は設定より強い

`weightCompanyName` や `duplicateThreshold` をどう変えても、正規化した企業名が完全一致したら必ず `similar` にします。
`duplicate.ts` の判定は「Reserved → 有効受注 → 企業名完全一致 → 連絡先完全一致 → スコア」の順で、スコア判定に落ちる前に打ち切ります。
旧設定(企業名40点・閾値50)ではスコアが44%で閾値に届きませんが、完全一致の分岐で `similar` になります。

### 1-2. 電話番号・Webドメインの完全一致も重複候補にする(設定でON/OFF)

仕様は企業名完全一致だけを特例としています。ただ実務では、企業名の表記が違っても電話番号やドメインが同じなら同じ拠点です。
そこで **既定ONの設定 `forceContactExactSimilar`** を追加し、電話番号かWebドメインが完全一致したらスコアに関係なく `similar` にします。
基本設定画面からOFFにでき、OFFにすると仕様どおりスコア判定だけになります。

### 1-3. 施設が違うときは即時停止にしない

Reserved案件や有効な受注案件に施設名が入っていて、今回の申請の施設名がそれと**異なる**場合は、即時停止(reserved / ordered)にしません。
「株式会社アルバフーズ 本社ビル」がReservedでも、同じ会社の別の工場までは止めない、という考え方です。
ただし企業名は一致するため、`similar` として本部の重複審査には必ず入ります。

どちらかの施設名が空欄のときは「企業全体」を指すとみなして一致扱いにし、即時停止の対象にします。

### 1-4. スコアの出し方

- スコア = (各項目のウェイト × 一致度)の合計 ÷ ウェイト合計 × 100
- 企業名・施設名の一致度は bigram の Dice 係数(0〜1)
- 電話番号は完全一致のみ 1
- Webドメインは完全一致で 1。片方がもう片方のサブドメインのときだけ 0.7
  - 「登録可能ドメインが同じ」では加点しません。`a.example.jp` と `b.example.jp` のような別会社を拾ってしまうためです。
- ウェイト合計で割るため、本部が合計100以外のウェイトを入れても0〜100に収まります

### 1-5. 弱すぎる候補は出さない

スコアが `min(25, 閾値)` 未満の候補は、画面にも審査キューにも出しません。閾値未満の切り捨てなので判定結果は変わりません。
審査画面が無関係な会社で埋まると、かえって見落としが増えるためです。比較画面は既定で上位3件、残りはボタンで開きます。

ただし、**企業名・電話番号・Webドメインが完全一致した候補と、営業不可の根拠になった候補は、スコアに関係なく必ず残します。**
企業名のウェイトを0にした場合でも、比較画面に「何と重複したのか」が出ないままにならないようにするためです。

### 1-6. 判定対象から外すもの

- 「営業不可」と判定済みの案件(`reviewState === 'blocked'`)は候補に含めません
- 解除したReserved案件(`active === false`)も含めません
- 案件詳細から再判定するときは、自分自身を `excludeDealId` で除外します

## 2. 正規化(§3.4)

### 2-1. 企業名

`NFKC正規化 → 小文字化 → 法人格の除去 → 記号・空白の除去 → もう一度法人格の除去` の順です。

最後にもう一度落とすのは、「Luxive株式会社。」のように**記号が挟まって取りこぼす**ためです。
記号を落としたあとに「luxive株式会社」となるので、そこで初めて「株式会社」を除去できます。

英語の法人格(`Inc.` `Ltd.` など)は、前後が英数字でないときだけ落とします。`Zinc` を `Z` にしないためです。

### 2-2. 電話番号

`+81` `+81 (0)` `0081` を国内形式へ寄せ、`内線` `代表番号` `ext.` `#` より後ろを捨てます。妥当性は10桁か11桁で見ます。

### 2-3. Webサイト

scheme・`www.`・パス・ポート・末尾のスラッシュとドットを落としてホスト名だけにします。
単一ラベル(`localhost` など)、ラベルが空、TLDが英字2文字未満のものは「有効なドメインではない」として `null` を返します。
表示は入力されたURLのまま残し、比較にはこの正規化値を使います。

## 3. 保護期間(§10)

| 起点 | 保護開始日 | 期限 | 既存より短くなるか |
| --- | --- | --- | --- |
| 営業予定登録 | 変更日 | 変更日 + plannedDays | する(新規のため実質関係なし) |
| 商談 | 既存を引き継ぐ | 変更日 + meetingDays | しない(既存が長ければ据え置き) |
| 見積提出 | 既存を引き継ぐ | 変更日 + quotedDays | しない |
| 受注確定 | 受注日 | 受注日 + orderDays | 仕様どおり受注日から数え直す |
| 追加受注 | 受注日 | 受注日 + additionalOrderDays | 同上 |

- 残り日数は保存しません。`保護期限 − 今日` で毎回計算します。
- 受注日を後から直した場合も、保護開始日・保護期限・最終受注日をその日から数え直します。
- 基本設定を既存案件へ反映するとき(§10.7)の起点は次のとおりです。
  - 受注確定: **取消されていない受注イベントのうち、いちばん新しいものの受注日**。それが追加受注なら `additionalOrderDays` を使います
  - それ以外: **現在のステータスへ最後に変更した活動日**。活動日の大小ではなく、記録された順番の最後を採ります(あとから過去日で「商談へ戻す」と入れた操作を尊重するため)。初回到達日(`firstReachedAt`)はダッシュボードの「商談数」用に別途保持しています

### 3-1. 受注イベントが変わったとき

初回受注の追加・修正、受注の取消、追加受注のいずれでも、**取消されていない受注イベント全体**から
最終受注日・保護開始日・保護期限を組み立て直します(`orderStateFor`)。単独の受注日では決めません。

- 過去日の追加受注を足しても、いちばん新しい受注が基準のまま
- 取消済みの初回のあとに新しい初回を作っても、より新しい追加受注があればそちらが基準

### 3-2. 受注を取り消したとき

取消されていない受注イベントだけを見て、最終受注日・保護開始日・保護期限を組み立て直します(`orderStateFor` / `rebuildAfterOrderChange`)。

- 追加受注を取り消した → 残っている初回受注の受注日から数え直す
- 受注をすべて取り消した → 受注前の段階(見積提出、なければ商談、なければ営業予定登録)へ戻し、その起点から数え直す。ダッシュボードの「有効契約・受注企業数」からも外れる

仕様に明文はありませんが、「取消したのに保護だけ残る」状態を避けるための決めごとです。変更履歴にも残します。

## 4. 案件の進み方(§11・§12)

- 「案件進捗・営業活動」からのステータス変更と、「提案・見積・受注情報」からの金額入力の両方で進みます
- 見積金額を入れて保存すると、営業予定登録・商談の案件は見積提出へ進みます
- 受注金額を入れて保存すると受注確定になり、初回受注イベントを作ります
- 初回受注がすでにある状態で金額を保存し直すと、初回受注イベントを差し替えます(追加受注にはなりません)
- 追加受注は §13 の専用画面から登録し、初回受注を上書きしません

日付(活動日・見積日・受注日)は空欄・不正な値を保存できません。画面で止め、ドメイン関数でも例外にします。

## 5. 商品マスター(§7)

- 代理店に見せる単位は商品名だけです。SKU・香り・サイズは本部の画面にしか出しません
- 案件詳細の商品行は「案件に保存済みの行」+「現在販売中の商品名」をマージします
- **停止中の商品は、案件詳細でも入力できません**(表示だけ残ります)。§7.2 が「新規入力の選択肢から除外する」対象に案件詳細の新規入力行を挙げているためです。過去の金額・提案対象はそのまま表示し、保存し直しても消えません
- 画像は JPG / PNG / WebP、2MBまで。未登録の商品には共通の代替画像(インラインSVG)を出します

## 6. 権限(§2)

- 画面のアクセス可否は `src/router/routes.ts` の1か所で定義し、メニュー表示とRouterの判定が同じ定義を見ます
- 案件詳細を開くときは、案件IDに対して `canViewDeal` を必ず再確認します
- 代理店ユーザー管理は代理店管理者が主体で、本部は閲覧のみです(仕様どおり)
- 通知は `recipientUserId` の完全一致だけで絞ります

## 7. 通知と申請者に見せる情報(§15)

- 重複審査・延長申請の結果は、申請した本人にだけ通知します
- 申請者側の重複候補には、**既存案件の企業名・代理店・担当者・連絡先・金額を出しません**。一致した項目(企業名/電話番号/Webドメイン/施設名)とスコア、保護状態だけを見せます
- 申請履歴には「重複判定(申請時)」と「審査結果(本部の判断)」を別々の列で出します

## 8. 企業・施設(§16)

案件とReserved案件から企業単位に集約して作ります。企業マスターを別に持たないため、案件を直せば企業側の表示も必ず一致します。

企業詳細には、関連案件のほかに次を出します(§16.2)。

- **初回・追加受注の履歴**: 受注日・区分・案件・商品名・金額。取消したものは薄く表示して残します
- **重複判定・審査の履歴**: その企業に対する申請(案件になったもの・照会だけのもの)の判定と審査結果
- **変更履歴**: 関連案件の変更をまとめて時系列で

## 9. ダッシュボードの内訳(§18.6)

「有効契約・受注企業数」だけは**企業単位**のカードなので、内訳も企業単位で出します。ほかのカードは案件単位のため、内訳も案件一覧です。カードの数字と内訳の行数が必ず一致します。

## 10. 二重送信と競合・権限の再確認

- 重複審査・延長申請の確定は、更新処理の中で「まだ未処理か」を確認します。二重送信しても通知・監査ログは増えず、保護期限も二重に延びません
- 引継ぎは、確定の時点で**いまも引継ぎ元が担当している同一代理店の案件**だけを動かします。画面を開いたあとに担当が変わっていた案件を巻き込みません。履歴には実際に動いた案件だけを残します
- **登録完了画面も、案件IDに対して閲覧権限を再確認します。** 案件詳細と同じ扱いです(§2.4)
- 延長申請の一覧は、一般ユーザーには**自分が出した申請だけ**を出します。代理店管理者は自社分を見られます(§2.3)

## 11. データの保存(§20)

- `luxive.db`(localStorage): 業務データ一式
- `luxive.session`(localStorage): ログイン中の利用者ID
- `luxive.eligibilityDraft`(sessionStorage): 営業可否照会からの引継ぎ。営業予定登録の**送信を始めた時点で削除**します
- `schemaVersion` が変わったときは初期データを作り直します。そのとき、**元のデータは `luxive.db.backup.v<旧バージョン>` へ退避**してから置き換えます(黙って消さない)。同じキーが既にあるときは `.2` `.3` と連番を足し、古いバックアップも上書きしません

## 12. 画面まわりで決めたこと

- 金額入力は `type="text"` + `inputMode="numeric"`。スマートフォンで数字キーボードが出て、上下スピナーは出ません
- 空欄と0円は区別して保存します。負数と数字以外は保存前に止めます。カンマは正しい3桁区切りのときだけ受け付けます
- 画面幅860px以下では、表を縦積みのカードへ切り替えます。横スクロールを避けるためです
- 本部の重複審査・基本設定はPC前提の情報量ですが、横スクロールは出ないようにしています
- 全画面の最上部に「試作版」の告知バーを出します。仕様書には無い追加ですが、先方に渡したときに本番の画面と取り違えられないためです。ログイン画面はAppShellの外にあるので、`App.tsx` の2つのreturnの両方に入れています
- 画面に出す文言では「モック」というカタカナ語を使いません。相手に通じないためで、「試作版」「動作確認用」に統一しています(`tests/e2e/preview-notice.spec.ts` で検証)
